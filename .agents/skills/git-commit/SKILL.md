# Git Commit (Git 提交规范)

## 概览
标准化 Git 提交信息，以维护专业、可搜索且信息丰富的项目历史。


## 何时使用
- 在将任何代码推送到远程仓库之前。
- 在完成一个工作单元（功能、修复、重构等）之后。
- 当被要求“提交更改”时。

## 核心模式
### 1. 标题格式
第一行（主题）必须遵循以下格式：
`<type>: <description>`

常见类型：
- `feat`: 新功能
- `fix`: 修补 bug
- `refactor`: 重构（即不是新增功能，也不是修补 bug 的代码变动）
- `docs`: 文档变更
- `test`: 增加测试或更正现有的测试
- `chore`: 构建过程或辅助工具的变动
- `perf`: 提高性能的代码变动

### 2. 语言要求
**所有提交信息（标题和正文）必须使用英文。** 即使任务是用其他语言请求的，提交历史也必须保持纯英文。

### 3. 信息正文
正文必须提供上下文和细节。其结构应回答以下问题：
- **Summary (摘要)**: 这是什么更改？
- **Implementation (实现)**: 是如何完成的？（涉及哪些模块、算法或工具？）
- **Effect (影响)**: 产生了什么影响？（消除了什么 bug？上线了什么功能？）

### 4. 约束条件
- **字数限制**: 正文不得超过 **200 个单词**。
- **格式**: 使用多个 `-m` 标志或临时文件来确保包含正文。

## 执行工作流
1. **起草**: 根据规则编写标题和正文。
2. **暂存**: 使用 `git add` 将相关更改加入暂存区。
3. **验证**: 检查语言（英文）、格式（`type: desc`）和正文内容。
4. **执行**:
    ```bash
    git add <files>
    git commit -m "<type>: <description>" -m "<Summary>. <Implementation details>. <Effects>."
    ```

## 常见错误与辩解
| 错误 / 辩解 | 现实与要求 |
|-------------------------|-----------------------|
| **在网上搜索规则** | **停止。** 仅使用此技能中定义的规则。不要在其他地方搜索“约定式提交”；遵循本地结构。 |
| **“信息太长了”** | 保持正文在 200 个单词以内。做到简洁但富有信息。 |
| **“我只想用单行信息”** | 单行信息仅适用于微不足道的更改（如拼写错误）。非琐碎的更改必须有正文。 |
| **混合语言** | 在提交之前，将所有想法翻译成英文。 |

## 红旗警示 (Red Flags) - 停止并重新开始
- [ ] 标题缺失 `<type>:`
- [ ] 正文缺失或只是重复标题。
- [ ] 信息包含非中文字符。 (注：此项在英文规范中为“包含非英文字符”，此处保留英文要求，指 commit message 必须全英文)
- [ ] 正文是冗长的文字堆砌（> 200 单词）。
